# HealthLake API contract

> HealthLake is a technical demonstration using synthetic data only.
> It is not a certified healthcare platform and is not intended or
> authorized to process real personal health data.

The machine-readable contract is [`openapi.json`](openapi.json) (exported from the code by
`scripts/export_openapi.py`; a test fails when it is stale). Interactive docs: `http://127.0.0.1:8000/docs`.
The API is read-only and is not a FHIR server.

## Authentication
Header `X-API-Key`. Keys are generated by `healthlake api-keys --hashed-out ... --plain-out ...` (run by the
bootstrap): the API reads only SHA-256 hashes; plain keys are written once to a `0600` file under `.secrets/`.

| Client (default) | Scopes |
|---|---|
| dashboard | read, ops |
| analyst | read |
| operator | ops |

`read`: `/v1/releases/current`, `/v1/summary`, `/v1/patients`, `/v1/encounters`, `/v1/diagnoses`,
`/v1/observations`, `/v1/medication-requests`. `ops`: `/v1/releases`, `/v1/quality`, `/v1/pipeline-runs`,
`/metrics`. `/health/live` and `/health/ready` need no key.

## Releases and pagination
- Every analytics response carries `release_id`. Default: the active release; `release_id=` pins a published one.
- Lists: `limit` (default 50, max 200) and `cursor`. The cursor is an HMAC-signed token containing the release id,
  the endpoint, a hash of the filters and the last ordering key. Following `next_cursor` keeps reading the same
  release even if another one is published meanwhile (tested), so there are no omissions or repetitions.
- Ordering is deterministic (keyset): patients by key; encounters/observations/medication requests by event
  time then key; diagnoses by number of conditions (desc) then code; pipeline runs by start time (desc).
- Changing filters while reusing a cursor, or tampering with it, returns 422.

## Errors
Body: `{"detail": "...", "error_code": "..."}`.

| Status | When |
|---|---|
| 401 | missing or invalid `X-API-Key` |
| 403 | key without the required scope |
| 404 | unknown or unpublished `release_id` |
| 410 | the release was purged by retention (also for a cursor pinned to it) |
| 422 | invalid parameter, inverted range, limit outside 1..200, bad or mismatched cursor |
| 503 | database unavailable, or no release published yet |

## Filters and dates
Dates are UTC, ranges are `[start, end)`; naive values are read as UTC; `end <= start` is rejected.
`source_id` is one of `horizon-central`, `horizon-nord`, `horizon-sud`. `code` accepts `[A-Za-z0-9.-_]{1,64}`.
All SQL is parameterised; the schema name comes from `ctl.release` and is re-validated before use.

## Data minimisation
No names, addresses, telecom, free text notes, raw FHIR resources or SQL access. Patients expose
`patient_key`, `source_id`, `gender`, `birth_year`, `birth_date_precision`, `deceased`.

## Examples (real responses use the same shapes)
```
curl -s -H "X-API-Key: $KEY" "http://127.0.0.1:8000/v1/summary"
curl -s -H "X-API-Key: $KEY" "http://127.0.0.1:8000/v1/encounters?group_by=day&start=2025-01-01&end=2026-01-01"
curl -s -H "X-API-Key: $KEY" "http://127.0.0.1:8000/v1/observations?group_by=code&limit=20"
curl -s -H "X-API-Key: $KEY" "http://127.0.0.1:8000/v1/patients?limit=50&cursor=<next_cursor>"
```
